# Local prototype delivery

The Auth Portal runs at **http://127.0.0.1:8210** from this checkout. It uses the dedicated `datum_sync.portal:app` entry point, a private PostgreSQL cluster and generated operator credentials. A private read-only legacy MCP adapter and an Office/PostgreSQL demonstration provider process run alongside it; the original workspace server and coding harness are not running as part of this deployment.

## Implemented

- Auth screens integrated into the supplied Datum-Sync v2 UI: dashboard, principals, approvals, access lab, MCP activity, credentials, activity and connection settings. The original source shell, stylesheet, Datum mark, icons and navigation are reused directly; the earlier separate portal design has been removed. Browser interaction drives real endpoints; refresh preserves database state.
- Additive migrations `016_auth_portal.sql`, `017_mcp_federation.sql`, `018_job_ownership_events.sql`, `019_mcp_flow_observability.sql`, `020_credential_access_management.sql` and `021_mcp_server_registry.sql`, leaving existing account admin flags and legacy identities unchanged. New credentials are random opaque values stored as hashes.
- One-use enrolment invitations and claims, operator approval, scoped baseline credentials, human-only durable issuance and principal lifecycle controls.
- Device authorization and S256 PKCE consent. Elevated access has an absolute authorization deadline, rotating refresh tokens and replay-triggered family revocation.
- MCP initialization and credential-bound sessions with locked admission, tier-filtered tool discovery and immediate authorization checks on calls.
- Deterministic MCP flow summaries and append-only event timelines cover parsing, authentication, session checks, authorization, local/federated dispatch and completion under the server-generated response trace. The operator MCP Activity view contains safe identifiers, byte counts, timings and normalized outcomes without request arguments, response bodies, credentials or upstream content.
- Managed upstream service credentials now have encrypted immutable versions, safe inventory metadata, bounded agent requests, narrow operator approval, exact-tool time-bound grants, test-before-activate rotation, global disable and immediate per-grant revocation. **Secrets & Proxies** evaluates current agent ancestry, tier and policy together with live credential and grant state; agents never receive the upstream value.
- An operator-owned MCP server registry adds vetted OfficeCLI and PostgreSQL providers from the UI, persists discovery without resetting tool controls, and supports global server/tool disablement plus per-agent tool revocation. The Office route is a bounded command-shaped compatibility fixture; the PostgreSQL route runs fixed parameterized reads over a real local sample table. Server and tool lifecycle events are distinct from request-flow logs.
- A service-authenticated loopback MCP adapter exposes repository-scoped legacy metadata plus job summary, listing, status, bounded logs, durable events and safe artifact metadata. Jobs retain display names and store stable portal principal IDs across direct, MCP, scheduled and automated submissions. The gateway persists its catalogue, projects bounded names, enforces exact per-agent tool grants and records calls without arguments or log content. Inbound credentials never cross the upstream boundary.
- A controlled database-backed resource provider: document read/write, and human-approved publication with frozen arguments, grant ceilings, current-authority checks and atomic result/audit persistence.
- Restriction preserves deny rules; restore does not reactivate revoked credentials. Disable and retirement withdraw credentials, sessions and pending authority.
- Cookie/bearer separation, CSRF checks, exact local origin/Host checks, bounded request bodies, local throttling, safe DOM construction and restrictive browser headers.
- Local management/client/verification commands, pinned Python environment, private system-package inventory, and Git history preserving the input snapshot and corrected plan.

## Repairs to supplied components

The v1 connection proxy now resolves and validates the destination used by its actual transport, preserves HTTPS SNI, refuses redirects, releases its database connection during upstream I/O and limits streamed response collection. Custom credentials cannot be forwarded along a redirect chain. Authentication password work runs outside the event loop with a semaphore and a second lockout check after waiting.

The supplied harness now defaults to authentication on, requires explicit strong session configuration, limits explicitly disabled authentication to loopback, and fails closed on missing principal fingerprints. Its MCP bridge applies the server allowlist to every source, uses per-server credentials, rejects non-loopback plaintext HTTP, and disables ambient proxy configuration and redirects.

These are source repairs, not a deployment of the harness or legacy server. The new portal's authority rules do not retroactively change the legacy `/agents` or OAuth flows. In particular, the legacy self-mint, sliding authorization, pending-call, restriction and session designs identified in the review still require migration or retirement before those surfaces can be used as the production auth plane. Shell/path shims remain unsuitable as a sandbox.

## Remaining production work

This implementation is a local prototype, not an assertion of production readiness or full completion of the v2 proposal. Still required: supervised upstream stdio packages and general provider onboarding, isolated untrusted execution, full multi-operator tenancy beyond the current MCP ownership seam, operational external key management and credential recovery, distributed abuse controls, audit retention and backup/restore, TLS hosting and service management, broader client interoperability tests and independent security review. Streaming response collection does not constitute a complete upstream resource-isolation policy; production egress needs workload-specific limits as well.

The browser uses an HttpOnly SameSite cookie on loopback HTTP. Public deployment needs TLS and Secure cookies, deployment-specific origins and reviewed network controls. Current process-local throttling assumes one local worker. Publication is transactionally safe because the fixture's side effect is a database insert; real external side effects will need an outbox/idempotency design.
